# CryptoSpend 前后端与记账流程审查报告

> 审查日期：2026-09-21
>
> 审查范围：`frontend/`、`backend/`、自动化测试、构建配置与现有产品规划
>
> 审查方式：静态代码追踪、前后端数据流对照、测试/静态检查/生产构建验证
>
> 本报告只记录问题与改进方案，未修改业务代码或数据库。

## 1. 结论摘要

项目的基础方向是可靠的：金额主要使用 `Decimal`/micros 表达，后端负责生成复式分录，交易、撤销、成本批次、报表和备份也都有相应测试。当前最需要优先处理的不是视觉改版，而是少数入口可以绕过这些会计约束，以及卡片结算/退款仍然信任用户重复输入的数据。

建议先停止扩展新表单，依次处理以下四类问题：

1. **手工加密资产支出与转账会绕过 FIFO 成本批次。** 这会让总账余额、成本批次和已实现损益互相不一致。
2. **卡片结算未验证所关联的授权是否真的是同一笔交易。** 退款也没有检查累计可退余额，且退款状态由前端布尔值决定。
3. **数量、账面 MYR 金额和估值汇率可由用户分别填写。** 三者不一致时会污染成本和持仓市值。
4. **启动数据采用全量 `Promise.all`。** 任一非关键报表失败都可能让已有账本看起来像“尚未初始化”。

完成上述修正后，再推进卡片资料自动填充、历史事件搜索、时区统一、图表比例修正和输入项精简。这样既能减少用户输入，也能避免“更快地录入错误数据”。

## 2. 优先级定义

| 级别 | 定义 |
| --- | --- |
| P1 | 可能造成账本、成本、余额或状态错误，或合法业务无法被正确记录；应优先修复 |
| P2 | 明显影响可靠性、统计解释或核心流程效率；应在下一阶段处理 |
| P3 | 可维护性、界面一致性或低风险体验问题 |

本次未发现需要立即停机的数据破坏问题（P0），但下列 P1 项目在有真实加密资产和卡片流水后会产生难以补救的历史数据偏差。

## 4. 详细发现与建议

### CS-01：手工加密资产支出与转账绕过 FIFO 成本批次（P1）

**现状**

- 手工录入表单允许选择 `EXPENSE` 和 `TRANSFER`，同时允许选择任意资产：`frontend/src/App.tsx:1280-1465`。
- 通用手工事件只创建借贷两条总账分录：`backend/app/ledger.py:163-191`。
- 通用事件仅对 `OPENING_BALANCE`、`SALARY`、`INCOME`、`REWARD` 创建 acquisition lot：`backend/app/cost_basis.py:200-237`。
- 专用交易和专用转账流程才会执行 FIFO disposal 或 lot 搬移：`backend/app/trading.py:1-398`。

**后果**

例如钱包中有 1 ETH、成本 RM10,000。若用手工 `EXPENSE` 记录 0.1 ETH、账面 RM1,500，资产总账会减少 RM1,500，但原成本批次仍保留 1 ETH/RM10,000，也不会生成已实现损益。之后再交易或转账时，数量、成本和损益会继续分叉。手工 `TRANSFER` 同样只移动余额，不移动 lot。

**最小修复建议**

1. 后端先限制通用 `MANUAL` 的 `EXPENSE` 只能使用 MYR；禁止通用 `TRANSFER`，强制使用已有专用转账接口。
2. 前端同步移除手工表单中的 `TRANSFER`，并在选择非 MYR 支出时引导到专用“加密资产消费/处置”流程。
3. 若产品确实需要直接以加密资产消费，再增加一个小而专用的处置入口：按 FIFO 消耗 lot，并生成费用/支出、资产减少和已实现损益分录。

**验收测试**

- API 无法绕过 UI 创建会破坏 lot 的手工加密支出/转账。
- 资产转账后，来源和目标账户的数量、成本合计保持不变。
- 加密资产消费后，剩余数量、剩余成本和已实现损益可由同一组 FIFO 分配复算。

### CS-02：卡片结算没有验证授权交易身份（P1）

**现状**

- 结算 API 只确认 `authorization_event_id` 指向一笔处于可结算状态的授权：`backend/app/cards.py:176-192`。
- 它没有核对 provider、provider account、card account、merchant、country 或资产是否与原授权一致。
- 结算成功后会把所选授权标记为 settled 并释放 hold：`backend/app/cards.py:394-401`。
- 前端选择授权后不会自动填充资料，用户必须再次填写上述字段：`frontend/src/CardCenter.tsx:156-200`。

**后果**

用户选中授权 A，却可提交交易 B 的商户和账户资料；系统仍会释放 A 的 hold。金额在结算时发生变化是正常业务，但交易身份和资金归属不应随意变化。

**最小修复建议**

1. 选择授权后，从授权事件自动填充并锁定 provider、账户、卡账户、商户和币种等身份字段。
2. 后端必须复核这些不可变字段；只允许时间、最终金额、资金腿、费用和类别等结算事实变化。
3. 若要支持分批 capture，服务器记录累计已结算金额和剩余授权金额，而不是仅使用单一 `SETTLED` 状态。

### CS-03：退款可超出原交易，状态由客户端决定（P1）

**现状**

- 退款服务会校验本次 refund legs 的合计，却没有校验“历史累计退款 + 本次退款 ≤ 原购买金额”：`backend/app/cards.py:427-527`。
- 原交易被标记为 `REFUNDED` 还是 `PARTIALLY_REFUNDED`，取决于客户端提交的 `full_refund` 布尔值。
- 前端要求用户重新选择原支出账户，并手工勾选是否全额退款：`frontend/src/CardCenter.tsx:204-212`。

**后果**

同一购买可以重复超额退款；用户也可以把小额退款标记为全额，或把全额退款标记为部分。净支出、报表和后续可退款余额都会失真。

**最小修复建议**

1. 后端从原事件及其历史退款计算 `refundable_remaining`，超出时拒绝提交。
2. `REFUNDED`/`PARTIALLY_REFUNDED` 由后端根据剩余金额自动决定，删除 `full_refund` 输入。
3. 从原事件自动取得支出账户、类别、provider 和币种；前端只要求选择原交易、输入实际退回资金及时间。
4. 明确定义汇率差和最小单位容差，避免用浮点近似判断全额。

### CS-04：数量、账面金额和估值汇率可互相矛盾（P1）

**现状**

- 手工表单同时要求用户输入原币数量、账面 MYR 金额和可选汇率：`frontend/src/App.tsx:1429-1447`。
- 后端 schema 只检查非负，没有检查 `quantity × rate = book value`：`backend/app/schemas.py:283-304`。
- 成本 lot 使用账面金额，但 RateSnapshot 使用另填的汇率：`backend/app/cost_basis.py:218-237`。
- 奖励入账也同时接收价值与汇率，存在同样问题：`backend/app/schemas.py:673-687`、`backend/app/cards.py:554-590`。

**后果**

10 USDT、账面 RM42.50、汇率 100 目前可以同时被接受。lot 成本可能仍是 RM42.50，但最新汇率会把持仓估值成 RM1,000。

**最小修复建议**

- 对产生账面价值的录入，只让用户输入“数量 + MYR 金额”或“数量 + 汇率”二选一，第三项由系统精确计算。
- 后端仍需验证三者关系，允许的差异只应来自明确的小数舍入规则。
- 自动计算字段显示为只读，保留来源和时间供审计。

### CS-05：卡片前端无法记录多资金腿、多退款腿和多费用（P1）

**现状**

- 后端 schema 和服务已经支持 `funding_legs[]`、`refund_legs[]`、`fees[]`。
- 前端结算固定发送一个 funding leg 和最多一个 fee；退款固定发送一个 refund leg：`frontend/src/CardCenter.tsx:156-212`。

**后果**

若 provider 同时消耗两种资产，或退款拆回不同资产，用户只能合并成一个虚假资金腿或漏记。这不是纯界面便利问题，而是无法正确表达已经由后端支持的事实。

**最小修复建议**

- 将资金腿、退款腿和费用改为可添加/删除的重复行；默认只显示一行，保持常见场景简单。
- 实时显示每组 MYR 合计和需要达到的目标金额。
- 未填写费用时隐藏费用资产、账户和估值字段；用户输入费用金额后再展开。

### CS-06：启动和刷新是全有或全无（P2）

**现状**

- 应用启动同时等待资产、账户、类别、事件、卡片、报表、Journey 等十多个接口：`frontend/src/App.tsx:216-277`。
- 全部请求完成后才设置核心状态；任一请求失败，核心资产和账户也不会写入 state。
- `ready` 随后可能为 false，界面会显示初始化入口：`frontend/src/App.tsx:520`、`581-589`。

**后果**

一个次要统计接口失败，已有数据库也可能看起来像空系统，并诱导用户再次初始化。写入成功后的全量 refresh 也可能因无关接口失败而让界面停在旧状态。

**最小修复建议**

1. 把资产、账户、类别、设置划为核心启动数据，先加载并决定是否已初始化。
2. 卡片、报表、Journey 等模块独立加载并显示局部错误/重试。
3. 使用 `Promise.allSettled` 或按模块并行请求，但不要让次要模块决定整个应用是否可用。

### CS-07：持仓只识别直接的“资产→MYR”汇率（P2）

**现状**

- 持仓估值只查询 `quote_asset_id == MYR.id` 的 RateSnapshot：`backend/app/cost_basis.py:398-417`。
- 交易快照始终保存为“卖出资产→买入资产”：`backend/app/trading.py:297-306`。
- MYR 买 BTC 时通常产生 `MYR→BTC`，BTC→ETH 则产生交叉汇率；两者都不能直接为 BTC 的 MYR 市值服务。
- 汇率录入界面允许任意 base/quote 组合：`frontend/src/App.tsx:1908-1916`，但没有提示哪些汇率能被持仓采用。

**最小修复建议**

近期可采用最简单规则：持仓估值只接受并引导录入“非 MYR 资产→MYR”的规范汇率；交易有 MYR 总值时，同时派生该直接汇率。后续确有需要时，再加入反向/交叉路径解析、路径来源和过期标记。

同时应明确一个唯一的 reporting asset。当前 Asset 没有 symbol 唯一约束，而 `myr_asset()` 会从多个 MYR 中取一条：`backend/app/models.py:31-43`、`backend/app/trading.py:52-56`。最简单做法是禁止重复创建规范 MYR，或在设置中保存明确的 reporting asset ID。

### CS-08：时间线柱状图不能跨行比较（P2）

**现状**

`frontend/src/ReportsCenter.tsx:352-365` 在每一行分别计算 `max(income, expense, 1)`。因此 RM10 和 RM10,000 都可能画成 100% 宽。类别图则正确地对整组数据使用同一个最大值。

**建议**

先计算整个 timeline 的共同最大值，再传给每一行。保留数值标签和 tooltip，使零值和极小值仍可读。增加一项组件测试：不同数量级的两行应产生不同比例的宽度。

### CS-09：前端和后端使用不同的日期/时区规则（P2）

**现状**

- 后端报表与 recurring expense 使用设置中的 IANA 时区：`backend/app/reporting.py:36-115`、`backend/app/recurring.py:52-74`。
- 前端报表默认日期和 recurring `as_of` 使用 `toISOString()` 的 UTC 日期：`frontend/src/ReportsCenter.tsx:44-45`、`frontend/src/App.tsx:91-93`。
- 多处显示直接使用浏览器本地时区，前端没有统一使用账本设置时区。

**后果**

在吉隆坡午夜后、UTC 日期尚未切换时，默认日报可能打开前一天。若浏览器时区与账本时区不同，事件显示日和后端统计分桶也可能不一致。

**建议**

启动时取得 settings，集中提供 `ledgerDate()` 和日期时间 formatter，并显式传入 `timeZone: settings.timezone`。服务端继续作为分桶权威；前端不要自行用 UTC 猜账本日期。

### CS-10：Journey 和事件跳转只覆盖最近 100 条（P2）

**现状**

- 全局事件列表调用 `/events` 默认只取 100 条：`frontend/src/api.ts:459`、`backend/app/api.py:556-573`。
- Journey 的事件选择器直接使用该列表：`frontend/src/ReportsCenter.tsx:460-469`。
- 固定支出的“查看事件”也在同一内存列表中查找，较老事件可能跳转失败。
- Journey 选择事件后仍显示所有资产，并要求用户重新填写数量和 MYR 金额；后端随后再拒绝超额分配：`backend/app/reporting.py:565-601`。

**建议**

- 事件选择器接入已有分页搜索 API，支持日期、描述和金额检索，不依赖全局前 100 条。
- 选中事件后只显示该事件实际包含的资产，并展示“原始/已分配/剩余”数量和 MYR 金额。
- 默认填入剩余可分配金额；用户只在需要拆分时调整。
- 所有“查看事件”通过 ID 单独读取，不能依赖当前列表缓存。

### CS-11：交易搜索存在旧请求覆盖新结果的竞态（P2）

**现状**

`frontend/src/App.tsx:1149-1177` 在筛选或翻页时发出异步请求，但没有 AbortController 或 request ID。若旧请求较慢，它可在新请求后返回并覆盖 state。项目中的月度概览已存在 request ID 模式：`frontend/src/App.tsx:196-214`。

**建议**

直接复用月度概览的 request ID 做法：只允许最后一次请求更新结果和 loading/error 状态。无需新增状态管理库。

### CS-12：MYR 金额显示没有统一到“分”（P2）

**现状**

`frontend/src/format.ts:1-7` 直接拼接 Decimal 字符串，`1.5` 不会显示成 `1.50`，超过两位的小数也会全部显示。现有产品规划要求最终报表按 sen 展示，并明确 HALF_EVEN 规则。

**建议**

使用字符串/Decimal 安全的统一 formatter：报表默认显示两位，数量和审计详情可使用独立的高精度 formatter。不要先转换成 JavaScript `number` 再格式化，以免重新引入二进制浮点误差。

### CS-13：测试存在日期依赖与并行偶发失败（P2）

**后端**

`backend/tests/test_recurring_expenses.py:44-77` 使用固定的 2026-09-08 到期日，却由生产代码读取真实“今天”。在 2026-09-21 运行时，预期 `overdue_count == 0`，实际为 1。生产逻辑本身符合当前日期，失败来自测试时钟不固定。

建议给 recurring 服务注入/monkeypatch `_today`，所有“当前日期”测试使用固定时钟，不要依赖执行日。

**前端**

默认并行运行曾得到 38/40，通过失败用例单独运行以及全套 `--maxWorkers=1` 运行均为 40/40。失败时两个 App 级测试停留在 loading，说明共享机器资源或测试清理存在偶发问题。

建议先检查 fake timer、未清理请求和全局 mock；在根因确认前，可在 CI 暂时固定合理 worker 数，避免把资源抖动误报成产品回归。

### CS-14：依赖和根目录生成物管理不一致（P3）

- `backend/requirements*.txt` 没有锁定版本，CI 与开发机可能安装不同依赖组合。
- 根目录已出现未跟踪的 `node_modules/` 和 `package-lock.json`，而根 `.gitignore` 未统一处理这些生成物。

建议决定根 `package-lock.json` 是否是正式的 workspace 依赖锁：若是则纳入版本控制；若不是则移除根 package 配置或忽略其生成物。Python 至少锁定直接依赖版本，并由自动化依赖更新流程维护。

## 5. 输入精简与自动填充方案

原则：**确定性资料自动填充并锁定；可从另外两个字段精确推导的第三个字段不再要求输入；存在多个合理选择时才询问用户。** 自动填充不能代替后端校验。

| 流程 | 当前重复/易错输入 | 可自动填充或计算 | 用户仍需确认 |
| --- | --- | --- | --- |
| 手工 MYR 收支 | 资产、常用借贷账户、类别、日期 | 唯一 MYR、按事件类型的默认账户、上次类别、账本今日日期 | 类型、金额、描述；类别有歧义时选择 |
| 加密资产取得 | 数量、MYR 金额、汇率三项 | 由任意两项算第三项并锁定；保存来源 | 数量及一个估值事实、账户、时间 |
| 卡片结算 | provider、卡账户、商户、国家、币种全部重填 | 从授权自动带入并锁定；显示授权与结算金额差 | 最终金额、资金腿、费用、类别、结算时间 |
| 卡片退款 | 原支出账户、类别、是否全额退款 | 从原购买取得资料；服务器算剩余可退和状态 | 实际退回资产/数量/金额、时间 |
| 奖励入账 | pending reward 已有资料仍需重填价值和汇率 | 账户、资产、数量自动带入；价值/汇率二选一并推导另一项 | 估值来源和入账时间 |
| Journey 分配 | 事件、资产、数量、MYR 金额均手填 | 搜索事件后只列事件资产，默认剩余可分配值 | Journey、拆分数值（仅需拆分时） |
| 费用 | 无费用时仍暴露资产/账户/估值字段 | 金额为空或零时折叠；输入后按上下文预选账户 | 非零费用和与默认不同的资产/账户 |

其他低风险 UX 改进：

- 手工录入成功后保留常用账户/类别，仅清空金额和描述；日期更新到当前账本日期。
- 把 reversal 的 `window.prompt` 和删除收据的 `window.confirm` 改为应用内确认界面，展示事件摘要与不可逆后果。
- 固定支出“记录/跳过”动作应在选择后自动滚动、聚焦或以小型面板出现，避免按钮位于页面下方而被忽略。
- Snapshot 页面目前只是显示 checksum，不应标注为 “SHA-256 VERIFIED”，除非前端或后端实际完成重新计算并比对；否则改成 “SHA-256 checksum”。
- Dashboard 的 “Posted events” 若包含 draft/reversed，应改名为 “Events” 或只统计真正 posted 的事件。

## 6. 建议实施顺序

### 阶段 1：先保护账本完整性

1. 限制通用手工加密资产支出/转账，补 API 级回归测试。
2. 卡片结算核对授权身份，退款由服务端计算剩余金额与状态。
3. 强制数量、MYR 金额和汇率一致。
4. 为卡片多资金腿/退款腿提供最小可用的重复行界面。

完成标准：任何入口都不能让 ledger、lots、hold 或退款状态产生不一致。

### 阶段 2：缩短常用记账流程

1. 授权→结算、购买→退款、pending reward→credit 全部自动填充。
2. 手工 MYR 收支提供安全默认值并减少不适用字段。
3. Journey 改为可搜索事件并按剩余额度自动填充。
4. 启动数据按核心/模块拆分，提供局部错误与重试。

完成标准：常见卡片结算不再重复填写身份资料，常见 MYR 收支只需少量事实输入。

### 阶段 3：统一统计解释

1. 修正时间线共同刻度。
2. 统一账本时区和日期 formatter。
3. 规范 MYR 汇率方向、唯一 reporting asset 和汇率新鲜度。
4. 统一 MYR 两位小数展示。

完成标准：同一交易在事件详情、持仓和报表中的日期与 MYR 值具有一致解释。

### 阶段 4：稳定自动化与开发环境

1. 固定测试时钟，定位前端并行测试清理/资源问题。
2. 锁定依赖并明确根 workspace 生成物策略。
3. 再考虑 CSV 导入、模板或批量录入；这些功能必须复用阶段 1 的后端校验，不能另开旁路。

## 8. 已有优点，应在修改中保留

- 金额和数量使用 Decimal 字符串/micros，并明确采用 HALF_EVEN，避免核心计算依赖二进制浮点。
- 后端生成和校验复式分录，前端不直接拼装任意 ledger entries。
- 交易、成本批次、撤销、历史 as-of、退款和报表已有较广测试覆盖。
- 报表服务端按配置时区计算日期边界，方向正确。
- SQLite 备份使用数据库 backup API，并执行 integrity check。
- 收据上传包含大小、扩展名、签名检查和哈希记录。

后续优化应复用这些现有能力，避免引入新的前端会计计算或第二套状态来源。

## 9. 完成判定清单

- [ ] 所有加密资产减少都能追溯到 FIFO disposal 或明确的 lot transfer。
- [ ] 卡片结算只能关联同一 provider、账户、卡片和商户身份的授权。
- [ ] 累计退款不能超过原交易，退款状态完全由服务器推导。
- [ ] 数量、MYR 账面值和汇率不能保存为互相矛盾的组合。
- [ ] 多资产结算/退款可在 UI 准确表达，合计由服务器复核。
- [ ] 次要报表失败不会让已有账本显示为未初始化。
- [ ] 前后端使用同一账本时区解释日期。
- [ ] 图表跨时间段采用共同刻度，MYR 默认显示到分。
- [ ] 老于 100 条的事件仍可搜索、分配和按 ID 打开。
- [ ] 测试结果不依赖真实日期，默认 CI 并行度下保持稳定。
